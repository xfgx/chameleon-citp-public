# Roadmap: «цензор как транспорт» и control-plane каналы

Документ описывает план реализации четырёх направлений, предложенных владельцем проекта:

1. **Censor-as-a-Relay** — сама функция вердикта ТСПУ (block-страница / RST) как модуляция данных.
2. **BGP-транспорт** — модуляция глобального состояния маршрутизации, читаемая через публичные сервисы.
3. **Мультиканальная доска объявлений** — комбинация BGP + DNS-зона + CDN-кэш + CT-логи.
4. **ТСПУ как общий оракул** — детерминированные правила цензора как синхронизированный генератор расписания и кодовой книги.

Принцип: всё это — **только control-plane** (команды ≤1 КиБ: next-entry, ключи, координаты). Пользовательский трафик идёт через существующий data-plane (mux/TLS), он не меняется. Каждый этап заканчивается тестами и живой проверкой на сети владельца. Записи о работе — в `agent.md`.

---

## Что уже реализовано (фундамент)

- **CAR-канал** (`cf_car.go`): нода выставляет биты (`SetBit`), клиент читает их как «чистый ответ / блок» через HTTP-запросы с токеном-триггером. Есть лабораторный `MockCensor` (`cf_mock_censor.go`). Это — ядро направления 1, но пока в лабораторном виде: триггер — наш токен, а не реальные правила ТСПУ.
- **DNS-маячок** (`cf_dns.go`): нода отвечает TXT-записями по своему поддомену, клиент читает UDP-запросом. Полезная нагрузка до 180 байт за чанк. Это зачаток плоскости «DNS-зона» из направления 3.
- **BGP (read-only)** (`cf_bgp.go`): чтение снапшотов и истории маршрутизации через RIPEstat (проверено живым запросом, 46 origins). Это половина направления 2 — только чтение.
- **Bulletin board** (`cf_bulletin.go` + `cf_board_remote.go`): HTTPS-доска на ноде + асинхронное зеркало на Cloudflare Worker (R2). Клиентское чтение — `cf_board_client.go` (poll + расшифровка по `cf_seed`). Это действующий канал «доска объявлений», который уже переживает блокировку IP ноды.
- **Автопилот** (`cmd/chamd/autopilot.go`): контур «профиль → план → исполнение» на Windows-клиенте. Именно сюда будут подключаться новые каналы как fallback-источники команд.
- **Самодетекция** (`tools/cham-detectors`): детекторы verdict-probing, txt-entropy, query-cadence, route-flap — мерило «заметности» наших же каналов.

## Этап A — Кодовая книга и помехоустойчивость (фундамент направления 1)

Цель: превратить лабораторный CAR в канал, пригодный для реального цензора.

- **A1. Кодовая книга из общего секрета.** Пути/символы и порядок окон выводятся из DRBG на сессионном секрете (тот же подход, что у flavors). Никакой предварительной передачи списка путей по сети — обе стороны вычисляют её одинаково. Никаких реальных запрещённых SNI в коде: сигнатуры — конфигурационные данные оператора.
- **A2. Кадрирование и FEC.** Вердикт-канал шумный (тайминги ТСПУ плавают): добавить в `cf_car.go` кадр с маркером начала, CRC и кодом с повторением (простой repetition/Reed-Solomon). Тесты на MockCensor с вносимым шумом (выпадение/инверсия битов).
- **A3. Случайный пейсинг вместо фиксированных 150 мс/бит.** Сейчас ритм константный — наш собственный детектор `query-cadence` такое ловит. Сделать логнормальные паузы (как в cover.go) и проверить, что детектор не флагает.
- **A4. Тесты**: unit (кодек, DRBG-синхронизация кодовой книги на двух сторонах), интеграция loopback, прогон детекторов против нашего трафика.

Критерий готовности: 8/8 бит сообщения восстанавливаются через MockCensor с 10% шумом; детекторы молчат.

## Этап B — Настоящий Censor-as-a-Relay против реальной ТСПУ

Цель: нода публикует «триггерный» контент, клиент читает биты по вердиктам настоящего ТСПУ.

- **B1. Режим trigger-host на ноде** (`cham-server -cf-car-trigger ...`): набор путей/виртуальных SNI, часть из которых сконструирована под правила цензора (конфигурируемо; дефолт — безобидные тестовые сигнатуры). Нода по биту «1» отвечает триггерным контентом, по биту «0» — чистым.
- **B2. Читатель в chamd**: при недоступности борда автопилот открывает CAR-чтение (N окон × символы) и восстанавливает команду (next-entry/ключ). Поллинг — только при деградации, чтобы не светить паттерн.
- **B3. Обратный канал (клиент→нода)**: клиент инициирует запросы, триггерящие RST-инъекцию ТСПУ в сторону измерительного endpoint'а ноды; нода пассивно наблюдает долю оборванных соединений (счётчик на ноде по conntrack/логу). Кодируется короткий ack/heartbeat.
- **B4. Полевая проверка** на сети владельца (ISP перехватывает DNS — подтверждено профайлером): замерить фактическую пропускную (бит/с) и ошибочность.
- **B5. Тесты**: MockCensor расширить режимами «RST вместо block-страницы» и «случайная задержка вердикта»; e2e тест publish→read по кругу.

Критерий готовности: на реальной сети команда ≤1 КиБ доставляется по CAR за приемлемое время (цель: десятки секунд) без срабатывания детекторов.

## Этап C — DNS-зона как публичная доска (направление 3, первая плоскость)

Цель: чтение DNS-маячка не прямым UDP к ноде, а через **публичные резолверы** (DoH) — тогда канал вообще не касается IP ноды.

- **C1. Инфраструктура**: зарегистрировать дешёвый домен; делегировать подзону (NS-запись) на ноду — нода становится authoritative для неё (DNSBeacon уже умеет отвечать).
- **C2. Читатель через DoH**: клиент шлёт TXT-запрос к 1.1.1.1/9.9.9.9 (`cf_doh.go` уже имеет `ResolveTXT`), публичный резолвер сам ходит к нашей зоне. Для ТСПУ это обычный DNS-запрос к публичному резолверу.
- **C3. Анти-кэш**: нода выставляет минимальный TTL и варьирует поддомен-метку (epoch в имени), чтобы кэши резолверов не отдавали старьё.
- **C4. Тесты**: unit (кодирование чанков), живой тест с реальным доменом через DoH к двум резолверам, проверка свежести (TTL).

Критерий: клиент читает маячок через публичный DoH, ни одного пакета к IP ноды.

## Этап D — Дополнительные плоскости доски (направление 3, остальное)

- **D1. CT-логи (бесплатно, без своей AS)**: нода выпускает сертификаты (Let's Encrypt) на поддомены, кодирующие данные в label'ах; клиент читает crt.sh по HTTPS. Узко (лимиты LE ~50 серт/нед/домен), но реально и глобально видимо. Парсер crt.sh + тесты на сохранённых ответах.
- **D2. CDN/anycast cache-топология**: нода праймит кэш на разных edges воркера; клиент различает edge по служебным заголовкам ответа (cf-ray и т.п.). Зависит от возможностей Cache API воркера — сначала исследование, потом решение.
- **D3. RPKI**: публикация/отзыв ROA — требует свой префикс (см. этап E), до тех пор stub с `ErrRequiresInfrastructure`.
- **D4. Комбинер каналов**: в `control_fabric.go` уже есть multi-channel publish/recover (board + DNS + CAR + BGP). Добавить CT и DoH-DNS как полноценные каналы; в автопилоте — политика выбора: board → DNS → CAR → CT (по доступности и цене).

Критерий: при выключении любых двух каналов команда всё равно доходит по оставшимся.

## Этап E — BGP-транспорт (направление 2)

Самое инфраструктурно-тяжёлое направление. Чтение уже работает (RIPEstat). Запись требует **своей AS или контролируемого edge-маршрутизатора** — до этого момента писатель остаётся `ErrRequiresInfrastructure`.

- **E0. Документ требований**: что нужно (AS, PI-префикс или /24 PA, сессия с транзитом), где взять, сколько стоит. Решение владельца — отдельный шаг.
- **E1. Схема модуляции (можно проектировать и тестировать заранее на моках)**: BGP communities как 32-битные теги-полезняк; AS-path prepending count как символ; окна announce/withdraw по расписанию из этапа F.
- **E2. Читатель**: доработать `cf_bgp.go` — опрос RIPEstat/RIS по расписанию, декодирование communities/prepending-эволюции во времени, фильтр ложных срабатываний (естественный churn).
- **E3. Самодетекция**: держать частоту UPDATE'ов ниже порогов нашего же `route-flap` детектора (например, ≤1 обновления в несколько минут) — иначе канал заметен всему миру, не только нам.
- **E4. Тесты**: мок-фиды RIPEstat, симулятор «нода-маршрутизатор» (можно на локальном BIRD/FRR в контейнере — отдельная задача, не на проде).

Критерий: на моковом/лабораторном BGP-стенде символ доходит от «ноды» до читателя; на проде — только после появления своей AS.

## Этап F — ТСПУ как общий оракул и генератор расписания (направление 4)

Цель: обе стороны предсказывают поведение цензора одинаково — это даёт расписание окон и порядок кодовой книги без переговоров.

- **F1. Модель правил**: автопилот накапливает профили сети (`data/netprofile.json`): какие пробы триггерят блок, статистика задержки RST, вердикты whoami. Хэш модели — общий «секрет среды».
- **F2. Вывод расписания**: DRBG(сессионный секрет ‖ хэш модели ‖ epoch) → окна CAR/DNS/CT, порядок символов, моменты опроса борда. Обе стороны считают одинаково и независимо.
- **F3. Эпохи и ротация ключей**: управляющие сообщения привязываются к эпохам расписания (защита от replay по времени).
- **F4. Тесты**: симулированный оракул (MockCensor с заданными правилами) — проверить, что две стороны с одинаковой моделью выводят идентичные расписания, а с разной — нет.

Критерий: совпадение расписаний на обеих сторонах в 100% эпох на симуляторе; на живой сети — устойчивая синхронизация ≥ суток.

## Сквозные правила для всех этапов

1. **Только команды**: каналы направлений 1–4 несут ≤1 КиБ (next-entry, ключи, координаты). Пользовательский трафик — как раньше через mux/TLS.
2. **Самодетекция обязательна**: каждый новый канал прогоняется через `cham-detectors`; канал не считается готовым, пока наш собственный детектор его ловит легко.
3. **Safe-by-default**: никаких реальных запрещённых SNI/сигнатур в коде и дефолтной конфигурации — только эталонные тестовые данные; настоящие триггеры — забота оператора ноды.
4. **Без инфраструктуры — честный stub**: всё, что требует своей AS/префикса/on-path станции, возвращает `ErrRequiresInfrastructure` и документируется, а не имитируется.
5. **Проверка вживую**: каждый этап завершается прогоном на сети владельца (Windows 11 ПК) + запись в `agent.md` с фактическими цифрами (не оценками).

## Зависимости и блокеры

- Этап E упирается в покупку/аренду AS+префикса — решение и бюджет за владельцем.
- Этап C упирается в регистрацию домена (недорого, но нужен аккаунт регистратора).
- Пересборка chamd.exe/APK после каждого этапа требует свободного места на диске контейнера (сейчас ~99% занято; нужно ≥3 GiB свободных) и, для Android, тулчейна JDK/SDK/NDK.
- Текущие открытые пункты основного roadmap (next-entry с борда в полном виде, перенос автопилота в mobilecore) продолжаются параллельно и не блокируются этими этапами.

## Порядок работ (предлагаемый)

A → B → C → F → D → E.

Обоснование: A и B дают главный результат направления 1 на реальной ТСПУ; C — самый дешёвый новый канал направления 3; F умножает ценность всех каналов (расписание); D добавляет избыточность; E — самый дорогой и инфраструктурно-зависимый, идёт последним и частично параллельно (проектирование E1/E2 можно делать раньше на моках).
