# KS — data-plane на keystream-инверсии ядра chaossync


> **Research update 2026-09-08:** [KS-R1 integration](KS-RESEARCH.md). Seal preserves length differences (+28 bytes); schedule-dependent synchronization is an offline result. Historical results below do not establish current DPI/TSPU evasion or finite-state cryptographic security.


Статус: **ядро + драйвер + живой прогон + продакшн-деплой**. Дата среза: 2026-09-01.
Код: `internal/chaossync/ks.go` + `cmd/ks-vpn`. Заменяет CDT в роли data-plane
(CDT снят с роли; код и документ CDT оставлены как лабораторная справка — идеи
CST и ротации переиспользованы здесь).

> Carrier-режим chaossync (CSK / Pecora–Carroll / S=32) **не тронут** — он остаётся
> control-plane (мелкие команды: ротация мастера, ip/port-геометрия, тайминги).

## 1. Идея (инверсия)

В carrier-режиме решётка — носитель, идущий по проводу (медленно: физика
синхронизации). В KS решётка — **локальный генератор keystream на обеих
сторонах**; по проводу идёт только `nonce‖ct`. Ключ никогда не передаётся.

- Та же 8-сайтовая CML-решётка Q16.48, те же `DeriveField` (само-валидирующийся)
  и `EpochInit` эпохи — переиспользованы из `map.go`/`schedule.go` без изменений;
  гейт Э1 и золотой хэш `29f2315f…` покрывают этот путь.
- Направления разделены `dirMaster`: c2n и n2c — независимые генераторы.
- Датаграмма c эпохи m: `k_c = SHA-256("ks-whiten-v1" ‖ c ‖ state_c)` — ключ
  ChaCha20-Poly1305 (дефолт; AEGIS-128L заявлен опцией — пока честный stub,
  в x/crypto проверенной реализации нет).
- `nonce_c = SHA-256("ks-nonce-v1" ‖ k_c)[:12]` — на проводе: маркер позиции,
  ничего не раскрывает.
- AAD = sid эпохи направления (`epochSeed(master, "ks-cst-v1"-dir, m)[:16]`) —
  CST-идея: выводится локально, на проводе не появляется.

## 2. Свойства по построению

- **Потеря не рвёт состояние**: решётка шагает по счётчику, не по прибытию.
  Потерянная датаграмма = потерянный IP-пакет; следующая расшифровывается.
- **Replay-окно**: приёмник держит скользящее окно ожидаемых позиций (8192)
  nonce→key; поглощённый nonce изымается (повтор отброшен); граница эпохи —
  straddle cur/prev (запоздалая датаграмма прошлой эпохи принимается один раз,
  забытая эпоха — никогда).
- **Ротация эпох бесплатная**: граница по общему счётчику времени (NTP),
  без in-band REQ/ACK-налога.
- **Probe-invisibility**: датаграмма, не прошедшая AEAD под текущим keystream,
  получает ноль ответа; адрес клиента нода учит только от валидных датаграмм
  (не от шума сканеров). Снаружи порт неотличим от фильтрованного.

## 6. Хаос-пол keystream (2026-09-01, Задача 1)

По замеру Э-A (прод-поля квазипериодичны, λ₁≈0) keystream-класс полей теперь принимает поле только при λ₁≥λ_min. Реализация: `FieldClassKeystream` (раздельно от `FieldClassSync` — sync без изменений), оценка `EstimateLambdaMax(field, iters)` — целочисленный Benettin-lite (Q16.48, телескопинг сдвигов, бит-идентичен Win↔Linux), отбраковка — детерминированно следующий кандидат из DRBG-потока эпохи.

Финализировано по замеру: **λ_min=0.5** (принятые поля λ₁∈[0.613, 0.839], приёмка 100%, ~2 мс/поле). Гейты: бит-идентичность полей обоих классов, все keystream-поля λ₁≥0.5, sync сходятся, детерминизм отбраковки; Э1 29f2315f… и golden (ks f93da420…, fieldclass 20164417…) целы и одинаковы на linux и windows/wine — M8-отбраковка Задачи 2 их не сдвинула (поля golden-векторов M8-чистые).

## 7. IPv6 /48 ротация источника клиента (2026-09-04)

6in4 (брокер 193.0.203.203 ↔ Myserv 198.51.100.10, `2001:db8:1::2/64`,
MTU 1480, `he6in4.service`) поднят на выходе; брокер маршрутизирует нам весь
/48 — доказано ответами на произвольные адреса пула (`…abcd::123`, `…5555::123`
— оба 2/2 до 2001:4860:4860::8888 с Myserv). Клиент (Windows) флагом
`-v6prefix 2001:db8:1::/48 -v6rot 5` каждые 5 с поднимает новый случайный
адрес пула на TUN (crypto/rand по хостовым битам; исключены адрес сети и
нижний /64 — там ::1 брокера и ::2 нашего конца). Прежние адреса —
SkipAsSource (Linux: preferred_lft=0): новые потоки и однопакетные
DNS/UDP/ICMPv6 уходят со свежего адреса сразу; живые TCP держат свой до
закрытия (требование протокола). Окно — 32 адреса, дальше старшие снимаются;
всё в ActiveStore, откат по Ctrl+C. ::/0 в туннель с пост-проверкой
(паттерн fulltun v3).

Ноды поадресно ничего не знают — «подхватывание» префиксное:

- RU: `2001:db8:1::/48 dev ks0` (возврат клиенту), v6 default в table 100
  dev ks1 (следует за ks-exit-on/off — они теперь управляют и v6; exit OFF =
  v6 честно обрывается в blackhole: у RU нет своего v6-аплинка);
- Myserv: `/48 dev ks0` (возврат в плечо RU), форвардинг v6, ip6tables FORWARD
  ks0↔he6in4, INPUT proto41 от брокера + ICMPv6 (PMTU обязан ходить);
- обе ноды: nft `ip6 ks6g/guard6` — из туннеля принимаются только источники
  нашего /48 (anti-spoof: мы не усилитель чужих адресов).

Флаг `-tunv6` на нодах транзита отключает глушение disable_ipv6 на TUN
(по умолчанию поведение прежнее — v6 глушится). Ядро keystream не тронуто:
golden Э1 29f2315f…, KS f93da420…, fieldclass 20164417… — все на месте
(selftest на RU после сборки).

Проверки: `go test ./cmd/ks-vpn ./internal/chaossync` ok (включая новые
TestRandV6*); gofmt/vet чисты (linux+windows); netns-стенд (ULA-аналог /48):
8 UDPv6 через KS до «интернета», 5 уникальных источников при -v6rot 2,
ответы вернулись, v4 ping 2/2; регрессия ks_ping.sh PASS; живой сквозной
прогон netns-клиент→prod :51820→Myserv→6in4→интернет: ping6
2001:4860:4860::8888 6/6, 179–240 мс, источник из реального /48.

Пределы (честно): ротация по таймеру, не «каждый пакет» для живых TCP
(невозможно без разрыва потока); Windows-прогон за владельцем (компилируется,
vet чист; netns-доказательство на Linux полное); нативный IPv6 провайдера ПК
может перекрывать туннельный ::/0 по метрике — в логе предупреждение;
Android (mobilecore) ротацию не получил — отдельный шаг; v6-DNS резолверы
(Яндекс/Google/Cloudflare/OpenNIC) доступны через туннель без жёсткой
привязки.

## 8. v6-ПРОВОД: датаграммы на случайные адреса routed-пула ноды (2026-09-04)

У RU-ноды свой 6in4 (брокер 193.0.203.203 ↔ 192.0.2.10, `2001:db8:2::2/64`,
`he6in4-ru.service`; proto-41 через firstbyte работает — доказано tcpdump).
Пул `2001:db8:2::/48` — проводной: нода держит его local на lo (anyip) и
слушает весь /48 тем же dual-stack сокетом; отвечает ровно с того адреса, на
который пришла датаграмма (IPv6 pktinfo; на сокете IPV6_FREEBIND — без него
ядро режет pktinfo-src из anyip-пула EINVAL, доказано пробником; фолбэк —
ответ с адреса туннеля). Клиент (`-peerpool6 2001:db8:2::/48`,
`-wire6rot 30`): каждая KS-датаграмма уходит со случайного свободного порта
(bind :0, пересадка по таймеру) на случайный адрес пула — блокировка «IP
сервера» пуста, надо блокировать весь /48. AEAD валидирует содержимое, не
адреса — скачки адресов/портов протоколу безразличны. Нет нативного v6 у
клиента — 5 подряд ошибок отправки → откат на v4-провод (`-peerhost`),
keepalive перепроверяет и поднимает обратно; откат строго на v4-конфиг
(learned v6-пир в v4-сокет не встаёт).

Разведение пулов (урок петли 2026-09-04): провод-пул ноды (5b4a) и
клиентский пул выхода (5b49, routed в ks0) не должны пересекаться и на
ИСХОДЕ: на RU правило приоритета 50 `from 5b4a::/48 to 5b49::/48 → table 101
(default dev he6in4ru)` — собственные ответы провода никогда не попадают в
TUN (иначе петля перезапечатывания, ~70k пакетов/с). Если клиент с
-v6prefix (туннельный ::/0) запускает и -peerpool6 — пул провода пингуется на
нативный v6-дефолт мимо туннеля (Windows: PinWirePool).

Тесты: unit (порт/цели/откат/проба); netns ks_v6wire_test.sh — inner-трафик
по v6-проводу 4/4, захват: каждая датаграмма на другой адрес пула, ответы с
hit-адресов, порты пересаживаются, обрыв v6-маршрута → v4 → восстановление
3/3; prod-прогон на RU против боевого :51820 с реальным пулом — принято и
отвечено с пула. Предел (честно): живой прогон Windows-клиента за владельцем
(нужен нативный v6 на ПК; без него — v4-откат); туннель Myserv (5b49)
08:05–08:15 пал со стороны брокера — внешняя зависимость, действие владельца.

## 9. ПОЛНАЯ рандомизация провода: случайный ИСТОЧНИК → случайная ЦЕЛЬ (2026-09-04, ТЗ владельца)

§8 давал случайную только ЦЕЛЬ; источник выбирал стек (один адрес,
менялся только порт). Теперь случайны оба конца КАЖДОЙ датаграммы.

Код: `cmd/ks-vpn/wiresrc6.go` (пул источников, кросс-платформенное ядро),
`wiresrc6_windows.go` (PowerShell: RA/DHCPv6-префикс, `New-NetIPAddress /128
-SkipAsSource`, bind с ожиданием DAD до 3с), `wiresrc6_linux.go` (IPV6_FREEBIND,
тот же sockopt 78, что и у ноды), вызов в `wirev6.go`.
Флаги: `-wire6src auto|<CIDR>`, `-wire6srcn N` (1..64, по умолчанию 16),
переезд набора — по `-wire6rot`.

Честная асимметрия энтропии: ЦЕЛЬ — случайные 80 бит из /48 на пакет
(ничего не надо назначать — anyip на ноде). ИСТОЧНИК тоже выбирается
случайно на каждый пакет, но из набора N заранее привязанных сокетов, а
не из всего префикса сразу: на windows/amd64 IPV6_PKTINFO на ОТПРАВКЕ не
реализован (`FlagDst: not implemented`), исходный адрес задаётся только bindом,
а каждый адрес проходит DAD. Адрес-на-пакет из всего /64 на Windows
недостижим без raw-сокетов/драйвера — не делаем вид, что сделали.

Откат ПО ПРИЁМУ, а не по ошибкам отправки (главный урок полевого прогона):
у владельца `sent` дошёл до ~1300 при `udpRecv=0` — WriteTo возвращал успех,
провайдер молча резал v6, порог `wireFailsToFallback` не срабатывал никогда,
и клиент вечно стучал в чёрную дыру (ничего не грузилось). Теперь
`watchdog`/`tick`: при `sentSince >= 20` и тишине `> 12с` — откат на v4,
перепроба каждые 60с; в строй возвращает только ФАКТ приёма (`onRx`),
успешная отправка больше ничего не доказывает. В логе стадий появилось
поле `провод=v6/источников:N` / `провод=v4-откат`.

Нода не менялась. Проверено внешним прогоном: брокер везёт ВЕСЬ /48 на RU
(пинги на `::1234`, `::dead:beef`, `abcd::123`, `7f21::9` — 3/3 каждый;
`ip_nonlocal_bind` возвращён в 0, ответы держатся на per-socket FREEBIND).
Значит потери были на стороне клиента/провайдера, не ноды.

Тесты: `gofmt`/`go vet` (GOOS=linux и GOOS=windows) чисты, `go test ./cmd/ks-vpn
./internal/chaossync` зелёные (golden-векторы ЦЕЛЫ, плюс новый
`TestWireV6SilenceFallback` — молчаливая дыра и возврат только по приёму).
Новый стенд `.tools/ks/ks_v6src_test.sh` (netns SA/SB, префикс источников local на
клиенте, anyip-пул на ноде): 22 датаграммы — 22 УНИКАЛЬНЫЕ цели, 10 разных
источников, 0 адресов вне своих префиксов, ответы доходят (`udpRecv=39
ingestOK=39 dropped=0`, inner-ping 4/4), обрыв v6 → откат на v4 → 6/6 и 3/3.
Сборка: bundle `ks-windows-client-20260904d.tar.gz` (v9, `CURRENT` переведён),
exe sha256 `0c071ab8…1f45d8`.

Предел (честно): живого прогона v9 на Windows-ПК владельца ещё не было —
ветка `Detect` (RA/DHCPv6) проверена только компиляцией и vet, а не на живом

## 10. FAIL-CLOSED провод и петлестоп v6 (v10–v11, 2026-09-04)

§9 закрывал ТЗ; живые прогоны на Windows-ПК владельца дали три отказа, и все три —
в клиенте, а не у провайдера. Формулировка §9 «провайдер молча резал v6» была
поспешной и отозвана — читать её с поправкой ниже.

| Прогон | Симптом | Причина | Лечение |
|--------|---------|---------|----------|
| 13:5x | `'или' is not recognized as an internal or external command` до старта | cmd.exe ломается на UTF-8-кириллице в теле `.bat` | BAT только ASCII, русский текст — в `README.txt` (v10) |
| 14:08 | `New-NetRoute: Instance MSFT_NetRoute already exists ... Error 87` | хвост маршрута от прошлого запуска в ActiveStore | идемпотентный `PinWirePool` с пост-проверкой (v10) |
| 14:08 | `wire6src: ... exit status 4` | слишком узкий фильтр `PrefixOrigin` в `Detect` | расширенный `Detect` + дамп `addr`/`route` (v10) |
| 14:22 | `tunRd` 23517 за 3 с (~100k пак/с), `loop=0`, `udpRecv=0`, сетевой адаптер проседает | pin упал (`exit 3`) при туннельном `::/0` — датаграммы провода ушли в свой же TUN → петля усиления | FAIL-CLOSED gating + v6-плечо петлестопа (v11) |

### 10.1 Корень петли (главный урок)

Цепочка событий 14:22, всё в одном процессе:

1. `v6rot` поднял туннельный `::/0 -> ks0` (штатно).
2. `PinWirePool` упал → у `2001:db8:2::/48` не осталось маршрута мимо туннеля.
3. Пул источников не поднялся (нативного v6 на машине нет) → сокет остался
   на `[::]` → стек выбрал источник с `ks0` (наш же `5b49:*`).
4. Датаграммы провода писались в собственный TUN, читались обратно,
   запечатывались и отправлялись снова: 23517 чтений за 3 с при норме ~110/с,
   дальше 51k → 184k за 2 с. Wintun захлёбывается — именно это владелец видел
   как «ломается сетевой адаптер».
5. Петлестоп тогда проверял ТОЛЬКО IPv4 (`buf[0]>>4 == 4` и dst == проводной IP),
   поэтому всю v6-фазу взрыва счётчик `loop` стоял на нуле.

### 10.2 Правило FAIL-CLOSED

v6-провод включается только при двух условиях ОДНОВРЕМЕННО:

1. `srcReady` — пул источников поднялся (есть нативный глобальный v6);
2. `pinned` — `rot.PinWirePool()` вернул `nil`, т.е. пул доказанно уведён мимо туннеля.

Иначе провод не создаётся вовсе (`wire6: FAIL-CLOSED: ...` с причиной) и клиент
честно работает по v4-проводу. `PinWirePool` теперь возвращает `error` (раньше
только логировал), а при отказе печатает всех кандидатов `::/0`
(`cand ::/0 if=... nh=... metric=...`) — без догадок о причине `exit 3`.

### 10.3 Петлестоп: оба плеча

`loopGuardDrop(p, peerIP4, wirePool6)` в `cmd/ks-vpn/main.go`:

- v4: dst (байты 16..20) == проводной IP ноды;
- v6: dst (байты 24..40) внутри пула провода.

`wirePool6` парсится ВСЕГДА, даже когда провод выключен: туннельный `::/0` поднимает
ротация независимо. Тест `TestLoopGuardDrop` проверяет оба плеча и три негативных
случая (обычный v4, обычный v6, пул при `wirePool6 == nil`).

Правило на будущее: **любое новое плечо провода получает петлестоп в той же
правке**, что и само плечо. Иначе первый же ошибочный маршрут даёт усиление.

### 10.4 Физическая граница клиента (установлена полем)

У машины владельца (`LAPTOP-4LN8TLJH`, Wi-Fi) **нет ни одного глобального
IPv6-адреса**: роутер отдаёт `::/0` через `fe80::1`, но не отдаёт префикс.
Два независимых доказательства: в дампе `Detect` ни одной строки `addr ...`,
только два `route ::/0`; в 54k пакетов Wireshark весь IPv6 — только link-local
`fe80::/10` (MDNS/LLMNR/MLD).

Следствие без украшений: случайные ИСХОДНЫЕ v6-адреса с этого ПК невозможны в
принципе — адрес источника обязан принадлежать интерфейсу. Варианты: v6 от
провайдера (нужен реальный префикс, не только дефолт); 6in4 на самом ПК (свой /64,
но внешний наблюдатель видит один v4 брокера); либо рандомизация только на
плече нода <-> выход, где нативный v6 есть.

## 11. Андроид-клиент v12: честное отключение и вкладка «Инструкция»

**Симптом.** Нажатие «Отключить» рвало связь с нодой, но не опускало VPN
на уровне устройства: значок туннеля оставался гореть.

**Причина (доказана кодом).** `stopKS()` отменял только контекст. Kotlin отдаёт
ядру `ParcelFileDescriptor.dup(...).detachFd()`, то есть второй дескриптор того же tun.
Android держит VPN-интерфейс живым, пока открыт хотя бы один fd, а читающая
горутина висела в блокирующем `syscall.Read` и проверяла отмену только *перед*
чтением — без входящего пакета она не выходила никогда.

**Исправление в `mobilecore/ks.go`:**

- `syscall.SetNonblock(tunFd)` + `os.NewFile` — чтение/запись через runtime-поллер,
  поэтому `Close()` гарантированно будит читателя (задержка не растёт).
- новые `ksTunFile *os.File` и `ksSock *net.UDPConn`; `stopKS()` закрывает оба
  после отмены контекста и сбрасывает `ksLastRx`.
- читатель различает `os.ErrClosed`/`EBADF` (выход) и `EAGAIN` (пауза 5 мс),
  так что спина на закрытом дескрипторе больше нет.

**`ChamVpnService.kt`:** порядок остановки `Mobilecore.stop()` → `tun.close()` →
`stopForeground(STOP_FOREGROUND_REMOVE)` → `stopSelf()`; добавлен публичный
`lifecycle: VpnLifecycleState` для UI и лог `туннель отпущен, сетевой интерфейс закрыт`.

**`MainActivity.kt` (правки точечные, новый тёмный дизайн сохранён):**

- пятая вкладка `TAB_HELP` + `buildHelpPage()` — 8 разделов инструкции на `card()`.
- навигация вмещает 5 кнопок: у `MaterialButton` сняты inset-отступы и `minWidth`,
  включён autosize 8–11sp, паддинги полосы `2/4/2/6dp`.
- `refreshNav()` больше не зависит от порядка детей — номер вкладки в `tag`;
  активная подсвечивается `cAccentDim`.
- `pollStopped()` опрашивает состояние каждые 250 мс (гейт 6 с) вместо глухой
  паузы 4 с; на время остановки статус «Отключаем…».

## 12. Многопользовательский хаб `ks-hub` (2026-09-04)

## 13. Админ-панель `ks-admin`: статистика без содержимого трафика (2026-09-04)

Отдельная служба на той же RU-ноде: HTTPS, вход по логину и паролю,
живая статистика по всем каналам KS и журнал ошибок.

**Требование владельца, зашитое в архитектуру: содержимое интернет-трафика
не читается и не хранится.** Собираются только метаданные: адреса и порты
внешних устройств, счётчики пакетов и байт, состояние служб, строки ошибок
из журнала systemd. Пакеты не перехватываются, `tcpdump`-подобного захвата
в панели нет вообще.

### 13.1 Состав

- `cmd/ks-admin/main.go` — сбор, реестр устройств, события, хранение.
- `cmd/ks-admin/collect.go` — четыре источника данных.
- `cmd/ks-admin/auth.go` — пароль (scrypt), сессии, лимит попыток, TLS-сертификат.
- `cmd/ks-admin/web.go` — API и одностраничный дашборд.
- Юнит: `.tools/ks/ks-admin.service` → `/etc/systemd/system/`.

### 13.2 Источники данных

1. `/run/ks-hub/status.json` — пользователи хаба: онлайн, внешний адрес,
   пакеты и байты в обе стороны, общие счётчики (`dropped`, `spoof`,
   `isolated`, `noRoute`, `noPeer`, `qfull`, `sendErr`, `v6drop`).
2. `/sys/class/net/<if>/statistics/*` — байты, пакеты, ошибки и потери по
   `kshub0`, `ks0`, `ksphone0`, `ks1` плюс скорость «сейчас».
3. `journalctl -u <unit> --after-cursor` — строки стадий и ошибок четырёх
   служб. Курсор запоминается, поэтому журнал не перечитывается целиком.
4. `conntrack -L -p udp` — внешние адреса и порты устройств на портах
   провода. **Важно:** в ядре ноды `/proc/net/nf_conntrack` отключён
   (`CONFIG_NF_CONNTRACK_PROCFS=n`), поэтому нужен пакет `conntrack`;
   файл остался только как резервный путь. Учёт байт включается
   автоматически (`nf_conntrack_acct=1`, закреплён в
   `/etc/sysctl.d/99-ks-conntrack-acct.conf`).

Записи conntrack живут около 30 с после последнего пакета, поэтому панель
ведёт свой реестр устройств: когда адрес появился впервые, сколько портов
использовал, сколько пробросил и когда был активен последний раз.

### 13.3 Что видно в панели

- Карточки: пользователи хаба онлайн, активные адреса, проброшенный трафик,
  пакеты, текущая скорость, число ошибок и предупреждений.
- «Пользователи многопользовательского хаба» — по каждому доступу.
- «Устройства на проводе» — живые соединения прямо сейчас.
- «Журнал устройств» — все адреса с момента запуска панели.
- «Туннели» — по каждому интерфейсу, с ошибками и потерями.
- «Службы» — стадии обработки (из туннеля → зашифровано → UDP принято →
  расшифровано → в туннель → отброшено) и время последнего приёма.
- «Ошибки и предупреждения» — строки из журналов, с дедупликацией
  («Повторов») и фильтром по уровню.
- График скорости за последний час (шаг 5 с).

### 13.4 Доступ и защита

- `https://192.0.2.10:51843`, сертификат самоподписанный.
- Пароль хранится как scrypt-хеш в `/root/build/ks-admin.conf` (0600).
- Смена пароля:
  `KS_ADMIN_PASS='новый' /root/build/ks-admin -setpass -conf /root/build/ks-admin.conf -user admin && systemctl restart ks-admin`.
- Сессия 12 ч в cookie `ksadm` (HttpOnly, Secure, SameSite=Lax).
- Форма входа защищена csrf-токеном: скрытое поле `csrf` + cookie
  `ksadm_csrf` (HttpOnly, Secure, SameSite=Strict, 30 минут), сверка
  постоянным по времени сравнением.
- Проверка источника (Origin/Referer) отклоняет только явно посторонний
  источник. Обезличенный (`Origin: null`) пропускается — за него
  отвечает csrf-токен, см. 13.7.
- Не более 6 неудачных попыток за 5 минут с одного адреса.
- Вход в панель не требует включённого KS-VPN: она слушает публичный адрес.
- `/healthz` открыт (проверка живости), все остальные пути требуют входа,
  `/api/*` без сессии отвечает 401.

### 13.5 Объём хранения (минимальный, как просил владелец)

- `/var/lib/ks-admin/stats.jsonl` — срез статистики раз в 60 с.
- `/var/lib/ks-admin/devices.jsonl` — срез реестра устройств раз в 60 с.
- `/var/lib/ks-admin/events.jsonl` — только ошибки и предупреждения.
- Каждый файл ротируется по достижении 16 МиБ (хранится один `.1`),
  в памяти держится не более 400 событий.

### 13.6 Честный предел

Для старых одиночных служб (`ks-vpn-node`, `ks-vpn-phone`, `ks-vpn-exit`)
внешний адрес клиента в журнал не пишется, поэтому адреса берутся из
conntrack, а байты — из счётчиков интерфейсов. Полные пер-пользовательские
счётчики есть только у хаба. Чтобы уравнять, в `cmd/ks-vpn` нужно добавить
необязательный `-status` (потребует пересборки и рестарта живых служб).

### 13.7 Разбор: «Запрос отклонён (проверка источника)» (2026-09-05)

Симптом: на `/login` при любом вводе логина и пароля панель отвечала
`403` и надписью «Запрос отклонён (проверка источника)». Вход из браузера
был невозможен в принципе, при этом `curl` с правильным `Origin` проходил.

Причина: панель отдавала заголовок `Referrer-Policy: no-referrer`. По
стандарту Fetch при такой политике браузер для POST-запроса подставляет
`Origin: null` и не присылает `Referer`. Старая проверка `sameOrigin`
сравнивала `Origin` с `Host` напрямую, для `null` получала пустой хост
и считала запрос посторонним.

Исправлено (`ks-admin/1.2`):

- `Referrer-Policy` → `same-origin`, браузер снова присылает настоящий источник;
- `sameOrigin` пропускает обезличенный источник (`null`, пустой,
  непарсируемый) и сравнивает хост без учёта регистра и порта;
- вместо этой защиты добавлен csrf-токен формы (double submit:
  скрытое поле + cookie `ksadm_csrf` с `SameSite=Strict`); без него POST
  на `/login` отклоняется;
- отказы пишутся в журнал: `отказ по источнику: origin=… host=…`
  и `отказ по csrf: ip=…`, посторонний источник — ещё и событие WARN.

Проверка боем на ноде (локально и через внешний адрес):

| Проба | Ожидание | Факт |
| --- | --- | --- |
| POST без csrf-токена | 403 | 403 |
| POST с `Origin: https://evil.example` | 403 | 403 |
| csrf + неверный пароль | 401 | 401 |
| csrf + `Origin: null` (браузер) | 303 | 303 |
| csrf без заголовка `Origin` | 303 | 303 |
| csrf + свой источник | 303 | 303 |
| внешний адрес, csrf + `Origin: null` | 303 | 303 |
