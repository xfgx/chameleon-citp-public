## Шаг 1 — Базовый деплой ноды (VPN + Control Fabric)

1. Скопировать `dist/cham-server-linux-amd64` на сервер (scp), сверить
   SHA-256 с указанным выше.
2. `cham-server -genkey -keyfile /root/cham-server.key` → публичный ключ
   отдать клиентам (в панель chamd).
3. systemd unit `cham-server.service`:
   - `-listen 0.0.0.0:9443` (основной VPN)
   - `-cf-listen 0.0.0.0:9444` (bulletin HTTPS)
   - `-cf-car-listen 0.0.0.0:9445` (CAR trigger-host)
   - `-cf-dns-listen 0.0.0.0:5353` (DNS beacon, до делегации зоны)
   - `-cf-seed <общий с клиентом seed>`
   - `-cf-board-url https://cham-bulletin.your-account.workers.dev`
   - `Environment=CITP_CF_BOARD_TOKEN=<новый ротированный токен>`
   - `-cf-car-trigger /root/car-triggers.txt` (после подготовки файла)
   - Restart=always, RestartSec=3
4. Файрвол: открыть 9443/tcp, 9444/tcp, 9445/tcp, 5353/udp; остальное закрыть.
5. Проверка: handshake с Windows-ПК владельца, строка «сеанс установлен» в
   журнале; запись в agent.md с фактами.

## Шаг 2 — Этап B4: полевая проверка CAR против реальной ТСПУ

Код готов (B1 trigger-host, B2 читатель в автопилоте, B3 обратный канал).
Осталось измерить вживую:

1. В servers.json на Windows-ПК у ноды прописать `cf_seed`, `cf_board_url`,
   `cf_car_url: http://<IP>:9445`.
2. Прогон: нода публикует кадр через кодовую книгу (PublishControl → CAR),
   клиент читает через реального цензора провайдера (автопилот: обрыв борда →
   pollCAR). Замерить: фактические бит/с, долю ошибочных бит, число retry.
3. Обратный канал (B3): клиент дёргает trigger-URL, нода считает оборванные
   соединения → ack/heartbeat. Замерить.
4. Самодетекция: cham-detectors против живого трафика (query-cadence,
   verdict-probing) — должны молчать.
5. Критерий roadmap B: команда ≤1 КиБ доходит за десятки секунд, детекторы
   молчат. Цифры — в agent.md (фактические, не оценки).

## Шаг 3 — Этап C: домен + DNS-зона через публичные резолверы

1. Владелец регистрирует дешёвый домен (ручной шаг: аккаунт регистратора).
2. NS-запись подзоны (напр. `c.<домен>`) → IP RU-сервера; DNSBeacon
   перевешивается на 53/udp.
3. Читатель C2 уже готов и проверен живьём (DoH 1.1.1.1 работает из
   контейнера): клиент шлёт TXT-запрос к публичному резолверу, тот сам ходит
   к нашей зоне — ни одного пакета к IP ноды с клиента.
4. Анти-кэш C3 уже в коде: эпохальные метки (DNSEpochLabel) + TTL=5.
   Живой тест C4: свежесть через два резолвера (1.1.1.1 + quad9).
5. Критерий C: клиент читает маячок через публичный DoH, ноль пакетов к
   IP ноды. Запись в agent.md.

## Шаг 5 — Этап E (BGP): что делается на сервере, чего не хватает

1. E0 (документ требований): своя AS (~аренда/регистрация через LIR),
   PI-префикс или PA /24, BGP-сессия с транзитом хостера (уточнить у
   хостера: многие RU-дедики дают BGP-сессию за доплату). Решение и бюджет —
   за владельцем. До этого писатель остаётся `ErrRequiresInfrastructure`.
2. Тем временем на RU-сервере — лаборатория (НЕ прод): контейнер с
   BIRD/FRR, симулятор «нода-маршрутизатор» (E4); E1 схема модуляции
   (communities как 32-битные теги, AS-path prepending как символ), E2
   читатель RIPEstat по расписанию из F; E3 — частота UPDATE ниже порога
   нашего route-flap детектора (≤1 обновления в несколько минут).
3. Критерий: на лабораторном стенде символ доходит от «ноды» до читателя.

## Правила исполнения (из roadmap)

- Только control-plane ≤1 КиБ; data-plane (mux/TLS) не меняется.
- Каждый шаг заканчивается самодетекцией (cham-detectors) и записью в
  agent.md с фактическими цифрами.
- Safe-by-default: никаких реальных запрещённых сигнатур в коде/дефолтах.
- Без инфраструктуры — честный stub, не имитация.
- Откат: старый бинарник/конфиг храним рядом (backups/), systemd restart
  возвращает прежнее состояние за секунды.
